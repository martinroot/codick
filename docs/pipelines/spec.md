# CoDick: JSON-пайплайны поверх Kanban — ТЗ для агента

Версия ТЗ: 1.0. Дата: 29 сентября 2026.

## 1. Задача

Реализовать в CoDick первый рабочий механизм автоматизированных агентских сценариев. Сценарий загружается из JSON, выполняется серверным исполнителем и отображается над Kanban-доской для выбранной карточки. На первом этапе визуальный редактор сценариев не нужен.

Одна карточка — один запуск сценария. Внутри запуска последовательно работают специализированные профили Hermes, инструменты, автоматические проверки и блоки получения данных от пользователя. Результат шага сохраняется и передаётся следующим шагам по явно указанным связям.

Ручного подтверждения результата нет. Ревью выполняется агентом, а переход определяется программным условием. Запрос данных у пользователя — самостоятельный блок сценария, а не разрешение продолжить работу.

При интеграции с другим сайтом тот же сценарий работает под капотом: сайт показывает вопросы, отправляет ответы и получает результаты через API. CoDick UI выступает встроенным клиентом этого же механизма для тестирования.

## 2. Перед реализацией

1. Прочитать AGENTS.md и инструкции репозитория.
2. Найти текущие маршруты dashboard, реализацию Kanban, механизм профилей и запуска сессий Hermes, файловое хранилище, авторизацию и миграции БД.
3. Проверить, что уже работает, а что является preview/mock. Не выдавать перемещение демонстрационных карточек за исполнение сценария.
4. Составить короткую карту интеграции: существующий модуль → необходимое изменение. Реальные имена файлов выбирать по репозиторию, а не создавать параллельный dashboard.
5. Использовать текущий backend/frontend и Bootstrap-компоненты. По возможности подключать функцию через существующие точки расширения. Новую БД или очередь вводить только при доказанной необходимости.

Это ТЗ задаёт целевое поведение и контракты. Пути модулей, методы Hermes и текущая схема Kanban здесь не считаются проверенными: определить их по коду и описать в результате работы.

## 3. Границы первой версии

### Реализовать

- Импорт, проверку и хранение JSON-шаблонов.
- Последовательное выполнение четырёх типов шагов: agent, tool, user_input, condition.
- Условные переходы и ограниченный цикл доработки после ревью.
- Сохранение результатов, попыток, событий и ожидающих запросов ввода.
- Исполнитель, переживающий перезапуск backend.
- Полосу шагов над Kanban, связанную с выбранной карточкой.
- Всплывающий чат и вкладку Data / API для user_input.
- API запуска, статуса, ответов, событий и получения файлов.
- Два предзагруженных примера: короткий тестовый и Word-сценарий.
- Фиктивный адаптер для детерминированной отладки без затрат на модели.

### Отложить

- Визуальный графовый редактор, параллельные ветки, fork/join.
- Маркетплейс и публикацию шаблонов.
- Автоматическое распределение по флоту и развёртывание серверов по SSH.
- Динамическое изменение маршрута агентом во время исполнения.
- Произвольный JavaScript/Python из JSON-шаблона.
- Пользовательские cron-сценарии. Внутренний планировщик ожиданий и таймаутов нужен уже сейчас.

Заложить возможность расширения, но не реализовывать отложенные функции.

## 4. Объекты системы

| Объект | Назначение |
| --- | --- |
| ScenarioTemplate | Версионированное описание маршрута и контрактов |
| PipelineRun | Конкретный запуск с неизменяемым снимком шаблона |
| StepAttempt | Один вызов шага, включая повтор и возвращение после ревью |
| InputRequest | Ожидаемые данные, чат, контракт ответа и срок ожидания |
| Artifact | Файл с метаданными и контролируемым доступом |
| RunEvent | Событие изменения состояния для UI и внешнего клиента |

Не хранить состояние выполнения внутри исходного JSON. Сохранить снимок шаблона и его hash в момент запуска. Обновление шаблона не меняет уже запущенные сценарии.

Карточка хранит run_id или связана с ним отдельной таблицей. Не создавать новую карточку на каждый шаг и не синхронизировать состояние через перемещение колонок.

## 5. JSON-формат v1

Поля верхнего уровня:

- schema_version: версия формата, в MVP "1.0".
- id, version, name, description: идентичность шаблона; version — строка.
- inputs_schema: JSON Schema исходного ввода.
- start_step: ID первого шага.
- limits: max_step_executions и max_rework_cycles.
- steps: массив шагов с уникальными ID.
- result: ссылки на итоговые выходные данные.

Все ссылки на данные задаются объектом {"ref":"..."}. Строки считаются литералами, а не выражениями. Допустимые корни: inputs, steps. Пример: steps.edit.output.document_ref. Разрешение ссылки не выполняет код и не читает произвольные пути ОС.

Общие поля шага: id, type, title, input, output_schema. Поля agent: profile, instruction, timeout_seconds, retry. Поля tool: tool, timeout_seconds, retry. Поля user_input: prompt, response_schema, chat, wait_timeout_seconds. Поля condition: cases и default. Для остальных типов next — ID следующего шага или null для завершения.

Для condition MVP поддерживает только операции eq, ne, exists, gt, gte, lt, lte и логические all/any. Пример ниже использует eq. Случаи проверяются по порядку; первый совпавший определяет переход. default обязателен. Произвольные выражения запрещены.

JSON Schema использовать для структурной проверки: required, type, properties, enum, additionalProperties, items. Выбрать одну поддерживаемую версию схемы и указать её в документации. Проверка схемы не гарантирует смысловое качество работы — для этого предусмотрен отдельный агент ревью.

### Пример Word-сценария

Имена профилей и инструмента в примере — логические идентификаторы. Агент реализации должен привязать их к реальным адаптерам. Если инструмент недоступен, сценарий показывается как unavailable с точной причиной; подменять DOCX текстовым файлом нельзя.

```json
{
  "schema_version": "1.0",
  "id": "word-edit",
  "version": "1.0.0",
  "name": "Edit Word document",
  "description": "Редактирование, автоматическое ревью, уточнение и сборка DOCX",
  "inputs_schema": {
    "type": "object",
    "properties": {
      "document_ref": {"type": "string"},
      "instructions": {"type": "string", "minLength": 1}
    },
    "required": ["document_ref", "instructions"],
    "additionalProperties": false
  },
  "start_step": "edit",
  "limits": {"max_step_executions": 30, "max_rework_cycles": 3},
  "steps": [
    {
      "id": "edit",
      "type": "agent",
      "title": "Внести правки",
      "profile": "word-editor",
      "instruction": "Измени документ по instructions. При наличии feedback исправь замечания. Сохрани новый документ как артефакт.",
      "input": {
        "document_ref": {"ref": "inputs.document_ref"},
        "instructions": {"ref": "inputs.instructions"},
        "feedback": {"ref": "steps.review.output.feedback", "optional": true, "default": ""}
      },
      "output_schema": {
        "type": "object",
        "properties": {
          "document_ref": {"type": "string"},
          "summary": {"type": "string"}
        },
        "required": ["document_ref", "summary"],
        "additionalProperties": false
      },
      "timeout_seconds": 600,
      "retry": {"max_attempts": 2, "backoff_seconds": 5},
      "next": "review"
    },
    {
      "id": "review",
      "type": "agent",
      "title": "Проверить результат",
      "profile": "word-reviewer",
      "instruction": "Проверь сохранность документа и соответствие instructions. Верни verdict accepted или rework и конкретные замечания. Не запрашивай ручное одобрение.",
      "input": {
        "original_ref": {"ref": "inputs.document_ref"},
        "document_ref": {"ref": "steps.edit.output.document_ref"},
        "instructions": {"ref": "inputs.instructions"}
      },
      "output_schema": {
        "type": "object",
        "properties": {
          "verdict": {"type": "string", "enum": ["accepted", "rework"]},
          "feedback": {"type": "string"}
        },
        "required": ["verdict", "feedback"],
        "additionalProperties": false
      },
      "timeout_seconds": 300,
      "retry": {"max_attempts": 2, "backoff_seconds": 5},
      "next": "review_route"
    },
    {
      "id": "review_route",
      "type": "condition",
      "title": "Маршрут по ревью",
      "cases": [
        {
          "when": {"op": "eq", "left": {"ref": "steps.review.output.verdict"}, "right": "accepted"},
          "next": "user_details"
        },
        {
          "when": {"op": "eq", "left": {"ref": "steps.review.output.verdict"}, "right": "rework"},
          "next": "edit",
          "rework": true
        }
      ],
      "default": {"fail": "Unexpected review verdict"}
    },
    {
      "id": "user_details",
      "type": "user_input",
      "title": "Получить дополнения",
      "prompt": "Укажите название итогового файла и дополнительные пожелания. Если дополнений нет, сообщите об этом.",
      "input": {"document_ref": {"ref": "steps.edit.output.document_ref"}},
      "response_schema": {
        "type": "object",
        "properties": {
          "output_filename": {"type": "string", "minLength": 1},
          "additional_instructions": {"type": "string"}
        },
        "required": ["output_filename", "additional_instructions"],
        "additionalProperties": false
      },
      "chat": {"enabled": true, "profile": "input-assistant"},
      "wait_timeout_seconds": null,
      "next": "finalize"
    },
    {
      "id": "finalize",
      "type": "agent",
      "title": "Применить дополнения",
      "profile": "word-editor",
      "instruction": "Примени additional_instructions. При пустой строке сохрани документ без дополнительных изменений. Верни ссылку на итоговый документ.",
      "input": {
        "document_ref": {"ref": "steps.edit.output.document_ref"},
        "additional_instructions": {"ref": "steps.user_details.output.additional_instructions"}
      },
      "output_schema": {
        "type": "object",
        "properties": {"document_ref": {"type": "string"}},
        "required": ["document_ref"],
        "additionalProperties": false
      },
      "timeout_seconds": 600,
      "retry": {"max_attempts": 2, "backoff_seconds": 5},
      "next": "export"
    },
    {
      "id": "export",
      "type": "tool",
      "title": "Собрать DOCX",
      "tool": "documents.export_docx",
      "input": {
        "document_ref": {"ref": "steps.finalize.output.document_ref"},
        "output_filename": {"ref": "steps.user_details.output.output_filename"}
      },
      "output_schema": {
        "type": "object",
        "properties": {"artifact_ref": {"type": "string"}},
        "required": ["artifact_ref"],
        "additionalProperties": false
      },
      "timeout_seconds": 120,
      "retry": {"max_attempts": 2, "backoff_seconds": 5},
      "next": null
    }
  ],
  "result": {"document": {"ref": "steps.export.output.artifact_ref"}}
}
```

steps.<id>.output означает последний успешный результат этого шага в текущем запуске. Историю всех посещений сохранять отдельно. Новое успешное редактирование делает предыдущее ревью устаревшим до повторной проверки; не позволять позднему ответу старой попытки заменить свежий результат. Возвращение на edit создаёт новую итерацию и применяет замечания к исходному документу в этом примере.

У user_input response_schema является схемой выходного результата. У condition выходных данных нет, только решение и событие перехода. optional-ссылка допустима исключительно при явно указанном optional и default. Во всех остальных случаях отсутствие данных — ошибка шага.

## 6. Проверка импорта

Перед сохранением проверить формат, типы блоков, уникальность ID, существование start_step, всех переходов и ссылок. Проверять недостижимые шаги, пути до завершения и обязательность лимитов для циклов. Сложные гарантии доступности данных при условных ветках дополнительно проверяются во время выполнения.

Проверить наличие профилей и tool ID через адаптер. Отсутствующий профиль/инструмент — понятная ошибка готовности шаблона. Такие шаблоны можно сохранить как unavailable, но запуск запретить.

Импорт того же id/version с тем же hash — идемпотентен. С другим содержимым — конфликт; предложить новую версию. Показать ошибки с JSON-путём и текстом: например steps[2].cases[0].next: unknown step.

## 7. Исполнитель

Работает на backend, независимо от вкладки браузера. Браузер только отображает состояние и отправляет команды/данные.

Цикл: взять готовый запуск → захватить lease → разрешить входные ссылки → сохранить попытку → вызвать адаптер → проверить результат → сохранить результат и событие → определить следующий шаг → повторить или завершить.

Не держать транзакцию БД открытой во время вызова модели. Обновление состояния, номер события и переход записывать атомарно. Один run в MVP выполняет один активный шаг. Lease с heartbeat и проверкой владельца предотвращает параллельное исполнение двумя диспетчерами.

Состояния run: queued, running, waiting_input, blocked, completed, failed, cancelled.

- waiting_input: ожидается InputRequest, модель не работает.
- blocked: неопределённый исход внешнего вызова или временно отсутствующая инфраструктура; требуется восстановление, а не approval.
- failed: ошибка контракта, исчерпанные попытки/циклы или таймаут без разрешённого восстановления.
- completed: все шаги завершены, итоговые ссылки разрешены и доступны.
- cancelled: Stop завершил запуск; поздние ответы не меняют его состояние.

У попытки: queued, running, waiting_input, completed, failed, cancelled, unknown. Хранить ordinal, iteration, входной снимок, output/error, timestamps, execution_id, idempotency_key и номер владельца lease.

Возвращение по rework увеличивает счётчик доработок; max_rework_cycles=3 разрешает три возврата после первичного выполнения. retry.max_attempts=2 включает первичный вызов и один технический повтор. Эти счётчики независимы. max_step_executions ограничивает общее число активаций шагов, включая condition; технические повторы учитываются отдельным лимитом retry.

Не повторять ошибку доступа, невалидный контракт или отсутствующий профиль бесконечно. Retry failed step — действие отладки: создаёт новую попытку, сохраняет историю и не переисполняет успешные предыдущие шаги. Определить явный лимит таких повторов. Повтор user_input создаёт новый request_id и инвалидирует старый.

После перезапуска восстановить queued, waiting_input и отложенные retries из БД. Для running сначала сверить execution_id с адаптером. Если результат неизвестен, поставить blocked/unknown; не повторять автоматически действие с возможными побочными эффектами. Вызов можно повторить только если адаптер гарантирует идемпотентность либо подтверждено, что операция не началась.

Ожидание пользователя не занимает worker и не запускает периодические LLM-вызовы. Таймауты хранить как deadline, технические повторы — как next_attempt_at. wait_timeout_seconds=null означает отсутствие срока; конечный срок переводит запуск в failed с input_timeout. Закрытие вкладки не отменяет сценарий.

## 8. Адаптер Hermes и инструменты

Исполнитель не зависит от конкретного метода запуска Hermes. Адаптер предоставляет логические операции: capabilities, submit, status/result, cancel и получение progress. Реальные методы определить по репозиторию.

Запуск передаёт run_id, step_id, attempt_id, profile, instruction, input, output_schema и idempotency_key. Возвращает execution_id. Профиль задаёт специализацию/настройки; каждой попытке нужна отдельная сессия или эквивалентная изоляция, исключающая смешение двух заказов.

Передавать агенту исходное задание и только связанные данные/артефакты, а не весь бесконечный transcript. Структурированный результат проверять на backend. Невалидный JSON не переводит шаг в completed; допускается ограниченная попытка исправления в пределах retry.

Tool-блок вызывает зарегистрированный инструмент с проверенной схемой входа. Не исполнять команду из произвольного поля JSON. Для инструмента сохранять его свойства: read-only/side-effecting, поддержка idempotency и cancel. Stop запрашивает отмену, но UI должен честно показывать, если внешняя операция уже необратимо завершилась.

## 9. Канбан и полоса сценария

Размещение: компактная панель над текущей доской, без нового редактора и отдельной большой страницы. Контролы: выбор импортированного шаблона, Load JSON, Run. При Run создать карточку и run атомарно; исходные поля/файл получить небольшой формой по inputs_schema.

При выборе карточки панель показывает её шаблон, статус и маршрут. Без выбранной карточки — краткая подсказка и запуск нового сценария. Панель не является общей стадией всех карточек.

Завершённые шаги сворачиваются до названия и отметки; остаются доступны по клику. Текущий раскрывает краткий прогресс и необходимые действия. Будущие показываются компактно. После возврата на доработку активен edit, ранее выполненное ревью отмечено как устаревшее. Полную историю циклов показывать в журнале; не рисовать бесконечные копии блоков.

Для condition можно использовать маленький значок перехода. Скрывать техническую проверку маршрута из основной полосы допустимо, но журнал должен её содержать.

Карточка показывает название заказа, текущий шаг, исполнителя, iteration/attempt, состояние, время обновления и значок ожидающего ввода. Маппинг: queued → Queued; running → Running; running на ревью → Review; waiting_input → Waiting for input; blocked/failed → Blocked; completed → Done; cancelled → архив/Cancelled.

Колонки обновляются исполнителем. Drag-and-drop не должен запускать шаги, обходить review или объявлять заказ выполненным. Для pipeline-карточек в MVP запретить ручную смену статусной колонки. Обычные карточки сохраняют существующее поведение.

Действия отладки: Stop, Retry failed step, Open input chat, View events, Download result. Run можно нажать повторно для нового независимого запуска. Источником правды служит backend, а не состояние frontend.

## 10. Всплывающий чат

При достижении user_input создать и сохранить InputRequest. UI показывает уведомление и кнопку Open chat; при открытой странице выбранного запуска можно автоматически открыть окно один раз, без повторного захвата фокуса после каждого обновления.

Вкладка Chat: prompt блока, переписка, прикреплённые доступные файлы, индикатор собираемых данных и недостающих полей. Отправка сообщения не означает немедленное продолжение сценария.

Input-assistant только помогает собрать response_schema. Он не меняет шаблон, маршрут, исходное ТЗ и результаты других шагов. После каждого сообщения возвращает candidate_data и недостающие поля. Продолжение происходит автоматически, когда ответ соответствует схеме и достаточен по правилам блока. Не заполнять отсутствующий пользовательский ответ выдуманными значениями. Нужные пустые значения, например отсутствие дополнительных правок, пользователь сообщает явно.

Если ответ неоднозначен, спросить уточнение. Полнота определяется данными, а не кнопкой Confirm. Конкретные обязательные поля и допустимые пустые значения задаются схемой/инструкцией; отдельного approval шага нет.

Вкладка Data / API: run_id, step_id, request_id, response_schema, пример ответа, текущие собранные данные и ошибки проверки. Кнопки Copy schema и Copy response JSON. Не показывать секреты, credentials, системные инструкции и приватные пути ОС.

Чат и данные сохраняются. После обновления страницы пользователь видит тот же request. Старый закрытый запрос остаётся в истории, но не принимает новые ответы.

## 11. Внешний API v1

Точные URL можно согласовать с текущими соглашениями проекта, сохранив семантику:

| Метод и путь | Назначение |
| --- | --- |
| POST /api/pipelines/templates/import | Проверить и импортировать JSON |
| GET /api/pipelines/templates | Доступные шаблоны и readiness |
| POST /api/pipelines/runs | Создать запуск из template_id/version и inputs |
| GET /api/pipelines/runs/{run_id} | Снимок состояния, текущий шаг, ожидающий ввод, результат |
| GET /api/pipelines/runs/{run_id}/events?after_seq=N | События для восстановления UI |
| POST /api/pipelines/runs/{run_id}/stop | Отменить запуск |
| POST /api/pipelines/runs/{run_id}/retry | Повторить ошибочный шаг |
| GET /api/pipelines/runs/{run_id}/inputs/{request_id} | Контракт текущего ввода |
| POST /api/pipelines/runs/{run_id}/inputs/{request_id}/messages | Сообщение/файлы для сбора данных |
| POST /api/pipelines/runs/{run_id}/inputs/{request_id}/response | Готовый структурированный ответ внешнего сайта |

Для response тело: {"data": {...}}. Схема проверяется тем же кодом, что используется в UI. Ошибка — 422 с JSON-путём поля, request остаётся открытым. Закрытый/устаревший request с новым ответом — 409. Повтор той же принятой операции с тем же Idempotency-Key возвращает сохранённый результат; другой payload с тем же ключом — 409.

Idempotency-Key обязателен для создания run, отправки сообщений и response. Первое принятие response и постановка следующего шага выполняются в одной транзакции. Конкурирующие чат и внешний API не могут дважды продолжить run.

В состоянии waiting_input возвращать request_id, prompt, response_schema и ссылки на разрешённые артефакты. В состоянии completed — result и доступные для скачивания файлы. Открытые webhook-доставки отложить; для MVP достаточно REST и событий, с SSE при наличии подходящего механизма проекта.

Событие содержит event_id, schema_version, run_id, step_id, attempt_id, request_id при необходимости, seq, occurred_at, type, payload. seq строго возрастает внутри run. Типы: run.created/started/blocked/completed/failed/cancelled, step.started/progress/completed/failed, input.requested/message/received, route.selected. Клиент дедуплицирует по event_id/seq и после разрыва догружает события.

Все операции проходят существующую авторизацию; внешнему сайту выдаётся ограниченный серверный credential с доступом к его запускам. Credential не помещается в браузер. Проверять владение run/request/artifact на каждом маршруте. CORS не заменяет авторизацию. Файлы передавать как artifact_ref; скачивание — через защищённый маршрут или короткоживущую ссылку.

## 12. Хранение и наблюдаемость

Использовать существующую подходящую транзакционную БД. Для одного узла допустим SQLite; не использовать общую SQLite по сети как мультисерверный механизм. Свои таблицы/миграции держать в пространстве CoDick, не править внутренние таблицы Hermes напрямую.

Сохранять шаблоны, снимки запусков, попытки, запросы ввода, сообщения, артефакты и события. В run хранить next_attempt_at/deadline, counters и текущую попытку. В attempt хранить execution_id и resolved input. В запросе — accepted response и момент закрытия.

Артефакты хранятся отдельно от больших JSON-полей: ID, filename, MIME, size, checksum, owner и storage reference. В log не писать ключи провайдеров и полные credentials. UI показывает понятную ошибку и технический error_code; подробности доступны в журнале без секретов.

## 13. Последовательность реализации

1. Аудит текущего кода и карта интеграции.
2. Формат, валидатор, миграции и импорт JSON.
3. Исполнитель и fake adapter; короткий сценарий agent → review → condition с возвратом.
4. user_input, сохранение ожидания, response API и восстановление после рестарта.
5. Связь с карточкой, полоса шагов, чат и Data / API.
6. Реальный адаптер Hermes и доступный DOCX-инструмент.
7. Сквозной Word-сценарий, проверки, документация и демонстрация.

Каждый этап должен давать рабочий результат. Не начинать редактор, флот и маркетплейс до завершения этого цикла.

## 14. Приёмка и обязательные проверки

1. Валидный шаблон импортируется; неверная ссылка/переход/тип даёт точную ошибку до запуска.
2. Два запуска одного шаблона не смешивают сессии, входы, чаты и файлы.
3. Ревью rework возвращает агенту замечания; accepted переводит к следующему блоку автоматически. Лимит прекращает бесконечную доработку.
4. user_input останавливает исполнение без фоновых LLM-вызовов; браузер можно закрыть, backend перезапустить и продолжить по ответу.
5. Неполный ответ вызывает уточнение; валидный ответ автоматически продолжает сценарий без Confirm.
6. Внешний клиент проходит тот же цикл через API; UI и API используют одинаковую проверку и механизм принятия ответа.
7. Дубли response и конкурентные ответы не запускают следующий шаг дважды. Повтор запуска с тем же ключом не создаёт вторую карточку.
8. Перезапуск во время tool/agent вызова сверяет execution_id; неизвестный исход не порождает слепой повтор побочного действия.
9. Stop запрещает новые шаги; поздний результат отменённой/старой попытки не меняет run.
10. Карточка и полоса показывают истинное состояние; устаревшее ревью не выглядит актуальным после нового редактирования.
11. Чужие run/request/artifact недоступны; неавторизованные ответы отклоняются.
12. Итоговый DOCX реально открывается и содержит ожидаемые изменения. Недоступный инструмент явно блокирует запуск, а не выдаёт фиктивный успех.

Основные автоматические тесты выполнять с fake adapter: успех, доработка, лимиты, неверный output, ожидание/рестарт, дубли, гонка ответа, отмена и неизвестный исход. Затем один реальный сквозной smoke-test с небольшим DOCX. Не дублировать тестами каждый Bootstrap-элемент.

## 15. Что агент должен сдать

- Реализацию в существующем проекте и перечень изменённых файлов.
- Миграции и инструкцию запуска без потери существующих данных.
- Описание формата JSON и два примера сценариев.
- Документацию API с примером клиента: start → waiting_input → response → completed → download.
- Краткую запись проверки: какие тесты прошли, что реально проверено с Hermes/DOCX, какие ограничения остались.
- Демонстрацию полного цикла без ручного одобрения, включая один возврат после ревью и один внешний ввод.

Критерий готовности: после загрузки JSON пользователь запускает карточку, видит прохождение шагов, отвечает только там, где сценарий запрашивает данные, и получает результат. Закрытие вкладки и перезапуск backend не теряют прогресс.
